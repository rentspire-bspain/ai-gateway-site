### The problem
The daily pre-launch QA fleet and the site-level half of the benchmark suite were blocked at the Vercel edge: every non-browser request to ai.spaincos.com got HTTP 403 with `x-vercel-mitigated: challenge` (Vercel Security Checkpoint, code 708 on `i.spaincos.com/.well-known/vercel/security/request-challenge`). The 14:00Z run reported 9/28 green — almost all failures were the challenge, not product regressions. A real browser passed, confirming the site itself was healthy.

### Root cause
Vercel system-level DDoS mitigation challenges all non-browser traffic (curl, Python urllib, Playwright Chromium) from this network. Verified not to be:
- user-agent (all tested UAs, including a real Chrome UA, still challenged),
- the bypass secret alone (header, query param, and cookie variants all still challenged — active DDoS mitigation is documented as un-overridable by a Protection Bypass token).

### The permanent fix (live and verified)
1. **Protection Bypass for Automation secret** generated by the owner in Vercel → ai-gateway → Settings → Deployment Protection. The harness now sends it as `x-vercel-protection-bypass` when `VERCEL_PROTECTION_BYPASS` is set (kept out of the repo).
2. **System bypass rule** (the fix that actually defeats system-level mitigation) created via the Vercel REST API (`POST /v1/security/firewall/bypass`): source IP `32.196.239.245` (QA fleet egress), scoped to `ai.spaincos.com`, note "ai.spaincos QA harness + benchmark fleet egress". Pro plan; takes effect immediately without publishing. Pro allows 10 per project.
3. **Harness hardening** (qa/prelaunch.py): `http()` now (a) injects the bypass header when the env var is set, and (b) retries `x-vercel-mitigated: challenge` responses with bounded backoff so a transient challenge can no longer zero out a whole run.
